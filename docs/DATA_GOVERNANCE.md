# Veylora — Data Governance and Source Notes

## 1. Current Data Source

The project's working event log is based on **BPI Challenge 2017**, a historical loan-application process dataset distributed by 4TU.Centre for Research Data.

The source description states that the log contains applications filed during 2016 and subsequent events up to 1 February 2017.

**Dataset DOI:** https://doi.org/10.4121/uuid:5f3067df-f10b-45da-b98b-86ae4c7a310b

Review the official dataset landing page and applicable terms before redistributing data, derived extracts, or public demonstrations.

## 3. Data Organisation

### Raw Data

`data/raw/` contains locally retained source event-log files.

Raw data should remain separate from processed analytical outputs.

### Processed Data

`data/processed/` contains CSV artifacts generated through offline analysis scripts.

The application reads configured artifacts through its data catalog.

### Synthetic Data

Synthetic experimental records are generated by the process simulator.

Synthetic records must remain distinguishable from historical source data. They are used to evaluate the experimental estimation workflow under controlled assumptions and must never be presented as actual loan applications or observed business outcomes.

## 4. Data Handling Rules

1. Do not assume that a dataset is anonymous or unrestricted merely because it is publicly available. Confirm applicable terms and privacy limitations.
2. Do not add raw XML event logs or processed case-level exports to a public repository by default.
3. Store only the data required for the analysis.
4. Avoid displaying case identifiers in screenshots or public demonstrations unless the data-use review explicitly permits it.
5. Record the dataset citation, acquisition date, source version, input fingerprint, and transformation details for each reproducible analysis run.
6. Keep synthetic experiment outputs separate from historical observations.
7. If using company data, obtain written authorisation and review processing purposes, controller/processor responsibilities, data minimisation, retention, deletion, and access controls before ingestion.
8. Review repository changes before publishing to ensure raw data and sensitive derived files are not included.
9. Do not treat the local prototype as an approved enterprise data-processing environment.

## 5. Data Provenance Requirements

For a reproducible analysis run, the following information should be recorded:

| Provenance field | Purpose |
|---|---|
| Dataset name | Identifies the source |
| Dataset DOI or source URL | Supports source verification |
| Acquisition date | Records when the data were obtained |
| Source version | Identifies the exact dataset version |
| SHA-256 fingerprint | Helps verify input integrity |
| Transformation script | Identifies the processing logic |
| Software versions | Records the execution environment |
| Output artifact names | Identifies generated analytical files |
| Execution configuration | Supports reproducibility |

**Current limitation:** The project identifies its dataset source and working analytical artifacts, but a complete, automatically generated provenance manifest for every analysis run is not yet established.

## 6. Data Dictionary

| Field | Meaning in current analysis | Validation required |
|---|---|---|
| `case:concept:name` | Application or case identifier | Identifier uniqueness and disclosure risk |
| `start_time` | First event timestamp for a case | Timezone and malformed timestamp policy |
| `end_time` | Last event timestamp for a case | Timezone and malformed timestamp policy |
| `duration_hours` | Elapsed difference between end and start event | Non-negative values; not active processing time |
| `event_count` | Number of event records associated with a case | Lifecycle records may not equal distinct work attempts |
| `Accepted` | Case-level dataset label | Meaning and relationship to final process activities |
| `CreditScore` | Recorded credit-score-like field | Zero semantics and prediction-time availability |
| `activity_count__*` | Activity-level aggregates | Exact event and lifecycle counting rules |

## 7. Known Data Interpretation Risks

### Elapsed Duration

`duration_hours` represents elapsed time between the first and last recorded events for a case.

It does not independently measure:
- Staff working time.
- Queue time.
- Active processing time.
- Time attributable to a particular employee or department.

### Outcome Semantics

The `Accepted` field is a case-level label. Its meaning should not be assumed to map directly to a single final activity without domain validation.

### Credit Score

Zero values are common in the working data. Their meaning and availability at the intended prediction time are unresolved.

They must not automatically be interpreted as genuine zero credit scores or missing values without supporting evidence.

### Activity Counts

Activity-level aggregates depend on event and lifecycle counting rules. Repeated lifecycle records should not automatically be interpreted as independent work attempts.

## 8. Privacy and Security Considerations

The local prototype does not provide:
- An organisational data-protection officer.
- Formal legal review.
- Certified information-security management.
- Enterprise authentication and authorisation.
- A complete data retention and deletion service.

Do not imply otherwise.

Before using company data, obtain appropriate approval and establish deployment-specific privacy, security, and governance controls.

## 9. Release and Publication Requirements

Before publishing the project or redistributing any data-derived artifacts:

- Confirm the dataset's current terms.
- Include the official source citation.
- Review raw and processed files for disclosure risks.
- Check Git history for accidentally committed data.
- Verify that screenshots do not expose case identifiers.
- Revalidate dataset counts against the exact source version.
- Keep synthetic experiment outputs clearly labelled.
- Avoid presenting analytical estimates as verified business impact.
